# Concrete decisions from independent review

These decisions resolve document ambiguity. They do not close runtime qualification blockers. Read the [original Claude report](reviews/claude-review.md) unchanged; [disposition](reviews/disposition.md) tracks every finding. The numbered ten phases remain unchanged.

## Trust model: compatible host session, restricted sandbox contexts (B16)

Choose **model A** from CR-02. Unsandboxed processes running as the authenticated session user are trusted local-session principals. Permit the explicitly supported privileged Wayland families to these host clients: capture, data control, layer shell/taskbar management, output configuration/power, lock creation, virtual input and the chosen IME integration. Each operation still obeys protocol role/seat/source/lock rules. Merely being trusted does not let a client bypass another lock owner's protocol object or read content while the compositor's lock policy forbids capture.

Sandbox-context connections do not receive those globals by default. Context identity comes from a trusted sandbox broker/connection provenance, never an ordinary app_id. Do not expose context-delegation globals to nested contexts. Treat unclassified transport connections conservatively until peer/session identity is established. A missing context tag is not a proof of OS-level sandbox confinement. Older/untagged Flatpak, plain bubblewrap and other connections without broker-attached context are classified as trusted host when they otherwise meet host credentials. This known limitation requires actual launcher integration before claiming sandbox restrictions.

This matches local IPC/config policy: same-user host processes can mutate IPC and user configuration, so the baseline **does not protect against a compromised unsandboxed host process or a sandbox explicitly granted host home/IPC access**. Such access can defeat compositor-only isolation. `security.portal_capture = "consent"` controls the portal flow, not a universal consent barrier against trusted host screencopy tools. A future strict mode requires end-to-end IPC/config/helper activation design and is outside baseline support.

Thus an idle-daemon-started locker, D-Bus/systemd-activated portal backend, input method, clipboard manager, and taskbar can connect through the normal session socket. No inherited-fd-only requirement blocks them. Private inherited connections remain an optional hardening technique, not the sole baseline path. Lock input is routed only into the current lock tree. Under model A, any authenticated trusted-host IME/virtual-keyboard client may type into that tree; no stronger per-program approval or protection against malicious host typing is claimed. Tagged sandbox injection is denied and ordinary compositor-wide key-monitor observers receive no password/lock input. Granting arbitrary host software OS privileges remains outside the compositor's threat boundary.

B16: design required by phase 2; integration qualified in phase 7 with idle-started locker, activated portal, clipboard, taskbar, tagged Flatpak denial, and host config/IPC mutation tests. A strict-mode claim is prohibited until a separate decision closes its stronger boundary.

## Capture across lock: retained session, opaque content (B18)

Choose **retain sessions and redact to opaque black**. `lock-redacted` is internal policy state, not a protocol pause event. Do not send terminal `stopped` merely because of lock. Keep source dimensions/identity, process valid frame requests with opaque black content, hide cursor and all lock UI, and avoid rendering ordinary desktop pixels for capture. Use bounded capture cadence and reusable safe black resources; no unnecessary desktop render is required.

Unlock rechecks source generation and grant validity. If unchanged/authorized, the existing stream resumes ordinary authorized content; otherwise stop/fail it permanently. Actual revocation, source destruction, or unrecoverable device failure ends the session according to protocol/backend contracts. A terminally stopped protocol session is never resurrected. The example share→lock→unlock journey means an already permitted stream sees black while locked, then the same permitted source resumes after revalidation.

At lock/revocation epoch change, reject new sensitive copy jobs immediately, suppress publication of queued stale frames, and replace future output with black where session retention applies. GPU work already submitted into consumer-accessible memory cannot be retroactively erased or revoked; it was authorized before the boundary. Record that limitation explicitly. Test no sensitive job is submitted after the boundary, no stale completion is newly published, black destination writes complete before `ready`, and unlock cannot retarget another window/output.

Track **capture destination leases** in addition to source read leases: owning buffer/import, destination dimensions/format, pending GPU write, completion fence, capture frame/session identity, and terminal result. `ready` is sent only after the write is safely complete under the protocol/backend contract. Destruction of destination resource/session suppresses messages to dead resources but does not free backing storage still being written. Failed frames retire source and destination consumers safely.

B18: decision designed in phase 3's ownership model, capture implementation/lock behavior qualified in phase 7, effects/fast paths requalified in phase 9. See CAP-09 and CAP-10.

## Smithay ownership/blocker strategy (B04 refinements)

At the inspected revision, retain a Smithay `Buffer` clone (or equally strong owned source reference) in each submission record. A renderer submission retains it until a backend completion fence is signaled; register a nonblocking event source for exportable fence fd, or use the library's supported completion mechanism. Scanout retention ends after replacement/disable page-flip retirement, not the flip that first displays it. Multi-consumer retention ends after all records retire. Never poll a fence in a busy loop or drop last ownership at CPU submit.

Use the syncobj acquire blocker before surface state becomes consumable. In Smithay, that can hold back the whole commit; do not promise to observe a new committed size before acquire readiness. The three conceptual readiness dimensions remain distinct in FluxWM but are not guaranteed independently observable through every library path. Layout can fall back to **previous** acquired state without accessing blocked state.

Choose no extra compositor transaction blocker for already acquired/valid commits initially: transactions coordinate target layout and presentation selection, rather than hiding otherwise ready client state. For implicit-sync DMA-BUF, use the pinned backend's supported readiness/blocker integration before sampling where required; spike and test the concrete fence interface in phase 3. Do not convert an implicit-sync path into unsynchronized reads. B04 phase 3 closes single-GPU implicit lifetimes; phase 9 closes explicit/multi-GPU extensions separately.

On explicit-sync surfaces, do not use `wl_buffer.release` as the correctness oracle. Account per commit and timeline point; signaling a timeline point also affects earlier points, so test unsafe client timeline reuse separately from compositor-owned consumer ordering. The selected Smithay path rejects unsupported buffer types such as SHM on syncobj surfaces; test that error. For an unused replaced commit, release within one dispatch/retirement cycle **after the replacement is processed**, with zero readers/imports. The controlled fixture has no other outstanding consumers; failure to meet this assertion remains a failed case and an integration issue, not a documentation-only exception.

## Config helper execution and budget contract

Spawn a fresh dedicated helper executable using exec-based process creation for each accepted reload. Parent-owned compositor/seat/DRM/input/display/IPC fds are close-on-exec and not inherited. Explicitly close every descriptor outside the helper allowlist before exec using the qualified spawn/close-range mechanism; do not rely solely on library close-on-exec defaults. Pass only bounded config data/result channels and selected read-only config-directory handles where modules need them. Set a minimal explicit environment; no host display, D-Bus, credential, or arbitrary library-search variables are required for pure evaluation.

Linux baseline hardening: `no_new_privs`, no privilege elevation, explicit fd/file-size/CPU limits and an address-space/RSS strategy tested against the allocator; exact process memory limits remain B15 qualification inputs, not a claimed 32 MiB RSS cap. The parent retains robust child identity (pidfd where available, otherwise unreaped-child ownership), applies a one-second wall deadline, kills only its child on timeout, drains bounded result data and reaps it. One active helper plus one coalesced latest reload request prevents abandoned-worker growth.

Instruction budget counts hook intervals cumulatively across all permitted Lua execution and remains exhausted after one million instructions. Budget errors can be caught, so they are advisory until the parent deadline enforces termination. Baseline schema evaluation **does not expose coroutines**, avoiding inheritance ambiguity; future coroutine support must share the cumulative budget and retain process supervision.

Baseline Lua allowlist: `assert`, `error`, `ipairs`, `next`, `pairs`, `pcall`, `select`, `tonumber`, `tostring`, `type`, `xpcall`; pure `math` excluding uncontrolled RNG state, bounded ordinary `string` helpers excluding `dump`, and bounded `table` operations. `utf8` helpers may be exposed with input/output limits. Remove `debug`, `io`, `os`, `package`, `require` unless replaced by the explicit constrained loader, `load`, `loadfile`, `dofile`, `collectgarbage`, raw metatable mutation/introspection, `coroutine`, FFI and native C-module loading. Host traversal never calls user metamethods. Native string operations still have wall-time/memory protection through process limits; instruction counting alone does not bound their cost.

Pattern syntax is Rust regex dialect with bounded engine compilation and memory settings. Helper returns normalized pattern strings and schema data only; **parent background work** compiles accepted patterns/action bindings before swap. Helper-side compilation is not required. Security policy changes follow the selected trusted-host model; they are visible in config diffs and cannot weaken lock invariants. There is no pretend strict-mode confirmation boundary in baseline A.

## Text/font blocker and early display changes (B17)

B17 requires a minimal font/shaping integration spike by phase 3 and full UI closure by phase 5. Choose actual Rust shaping/font-discovery/rasterization dependencies only after their API/build/font licensing checks; source availability is insufficient qualification. The contract requires shipped or declared fallback fonts, accessible semantic labels, bidi/graphemes, color-emoji policy (supported or clear monochrome fallback), per-scale glyph atlases, zoom-aware cache reuse, effect/transformed text correctness, and bounded cache memory.

Phase 3's developer display preview needs no text UI: use a developer-only native stdin/TTY acknowledgement source and a 15-second automatic safe revert, implemented in phase 3 independently of future fluxctl. On-screen confirmation with shaped labels and semantic data-model nodes is phase 5; AT-SPI/Orca qualification is phase 8. If no acknowledgement/recovery path exists, do not expose risky mode changes interactively. Startup diagnostics in early phases use stderr/terminal; accessible startup feedback belongs to the supported complete session.

## Lock power, suspend, and assistive input

Before confirming lock, disable normal scanout/overlay/cursor planes and present safe coverage on every active output. For a powered-off/inactive output, establish a completed atomic state with every plane cleared of desktop framebuffers or the output disabled. A backend-proven disabled state counts as no active content to present; do not wake a monitor merely to lock. Every enable path while locked first tests and commits black/lock content, with no stale plane/cursor reuse. OUT-09 asserts no lock-caused wake and black/lock as the first subsequent framebuffer. This is a chosen backend contract requiring B08 protocol/KMS/hardware verification, not a claim that any driver already satisfies it. If it cannot be guaranteed, use a documented safe active-black fallback only on that qualified backend, or refuse successful lock; never override the protocol's security requirements by a boolean. Disconnected outputs leave the active set through authoritative removal. With zero outputs, no output content is active, while input/capture stay locked and hotplug starts black. Session-inactive/no-device-control routes defer confirmation until safe coverage can be proven and cannot claim a successful suspend lock otherwise.

The supported idle route uses privileged output-power control; implement and qualify it in phase 7. Suspend integration holds the supported bounded delay/inhibitor contract, immediately installs compositor-owned blanking independent of locker readiness, and waits for safe lock confirmation before releasing the delay when policy permits. Failure to establish coverage within the available suspend contract is a release blocker for that route, not permission to claim a successful lock. Final timing is measured against the supported session manager.

Lock UI is never exported by normal capture; existing streams receive black. Permit trusted-host IME/virtual-keyboard input only toward the current lock-associated tree, with password text/private candidates excluded from observers and screenshots. Test non-Latin password entry and touchscreen-only unlock. No input is delivered to normal applications while locked. Trusted host software can type into the locker, consistent with model A; tagged sandbox input and compositor-wide accessibility key observation cannot bypass lock routing.

## Effort and infrastructure

Withdraw the old 38–76 person-week forecast. No evidence supports a total schedule. Phase 1 produces a work breakdown with uncertainty per contract; phase 3 re-estimates backend and infrastructure, phase 7 re-estimates compatibility work. Budget hardware access, repeated driver installs, capture/latency equipment, VKMS CI, WLCS adapter work, fuzz/soak runners, accessibility testing, and maintenance explicitly. Owner roles need real assignments before implementation commitments.

New capture sessions/grants requested while locked are denied without exporting source metadata or lock UI (CAP-12). Only already authorized sessions remain alive with black frames. `capture = allow` in metadata rules means ordinary eligibility if there is no sticky private mark; it never clears a sticky deny. A trusted explicit compositor action is required to clear that mark.

Within one rule evaluation, `capture` uses **deny-first** merging: if any matching rule denies capture, the result is deny and becomes sticky before any allow is considered. Existing sticky deny also wins. Allow is eligible only when neither condition holds; it does not grant capture-protocol authority. All nonprivacy fields keep ordinary later-wins merging. Explicit trusted user clearance removes stored sticky history but cannot override a currently matching deny rule without changing that rule.
