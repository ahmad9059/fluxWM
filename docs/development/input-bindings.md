# Keymap-qualified input bindings

The nested compositor now compiles its existing development controls into a Rust binding table against the actual seat keymap. The new `flux-input` component prepares schema `Binding` values without retaining a native XKB object, seat, device or Lua VM. [Runtime startup/manual reload](runtime-config.md) now prepares user bindings against a serialized copy of that same fixed seat map on a worker. Evaluation success remains distinct from publication.

## Compilation and matching

Compilation validates the shared key/action schema, resolves case-sensitive xkb keysym names, rejects unknown names, rejects aliases that resolve to the same symbol/chord, and rejects code/symbol overlap on the same key in any configured layout. It scans the base level of each key/layout and keeps action storage once per binding. A chord absent from those base levels is rejected for user preparation; development defaults can retain an explicit inactive-index list so a foreign keymap need not fail solely because a Latin shortcut is absent. Physical evdev code bindings do not require a symbol assignment, and do not prove a physical device with that key exists.

Matching uses the current group's base symbols and exact effective Ctrl/Alt/Shift/Super modifiers. Caps/Num lock do not select a different binding. Level3/Level5 modifiers suppress matching because schema v1 cannot name those modifiers. Letter keysyms remain lowercase, with Shift explicit. For example `Alt+Shift+c` matches the base `c` key while Shift is active. A US plus shortcut is represented by base `equal` plus explicit Shift; `plus` can be a base symbol in a different layout. The built-in table includes those declared development alternatives. It is not a physical-key layout-agnostic shortcut system.

Smithay's actual pinned winit implementation adds eight to its key event code, and `KeysymHandle::raw_code` retains that XKB code. The backend trait's evdev wording is insufficient evidence for this adapter. Runtime matching subtracts eight once with checked conversion; physical binding codes are evdev. Press/release suppression remains keyed by the original seat code, preserving consumed-key ownership through modifiers, host-focus loss and late releases.

The compiler checks an actual key press/release against each resolved chord with Caps/Num lock variants. Triggers changing modifiers or groups are rejected until an explicit transition/tap policy exists. This rejection is fatal even with `RetainInactive`, which tolerates only absent base symbols. This closes a real compiler gap: `Alt+Shift_L` and evdev 42 with Alt compiled as active, but Smithay updates Shift before invoking the filter, so their exact modifiers never matched. Tests also supply a shifted level with an explicit Control action, a group-switching F1 action, and actions present only with Caps/Num lock or only in group two. Separate mutations dropping lock variants or probing only group zero fail those named tests. This is not complete sticky/latched accessibility, custom-keymap or native-device qualification.

Starting admission budgets are 4,096 bindings, 4 MiB total binding/action string bytes, the fixed evdev domain 1–767, 32 layouts per key and 65,536 resolved key/layout/chord entries. The compiler queries that fixed domain rather than relying on a native key iterator that cannot stop early. These constrain this compiler's admitted tables/expansion, not whole-process RSS, a universal compile deadline or dispatch latency. Compilation belongs before dispatch or in background preparation; keymap replacement must recompile and publish the corresponding table coherently. The current runtime has no keymap replacement path.

## Runtime and evidence

The development table keeps Alt direction/move, mode, close/quit, spawn and width controls. Diagnostics expose only table source, entry/inactive counts and unavailable runtime keymap changes, not key identities. Runtime config capabilities report manual reload when loading is enabled; unsupported setting categories remain explicit in effective settings. The binding compiler validates action data; it does not authorize an action or implement currently unavailable window/lock features.

The component tests use actual libxkbcommon maps for US, Russian and US/Russian groups, real lock/state updates, alias collisions, physical/symbol ambiguity and synthetic XKB actions. The modifier-trigger regression fails against the earlier compiler and passes after rejection is added. Private authenticated Xvfb regressions exercise real Alt+c/s routing, consumed releases, held keys/buttons and popup cancellation. This is separate from physical code binding end-to-end, full shortcut/menu inhibition or real-device coverage.
