# Native primary-plane submission and reverting preview

The optional driver now connects synchronized GBM/GLES RGB targets, full-cookie atomic commits and the owned frame ledger. `begin_output_preview` captures rollback state and tests both configurations before a blocking initial modeset without flip events. This avoids requesting events for other touched CRTCs that stay off. `submit_preview_frame` admits a new frame only after the pending completion; the existing DRM source advances the matching queue. `finish_output_preview` invalidates publication, performs blocking atomic rollback and then retires consumer resources. Main `fluxwm` remains nested-only; this is a native backend component, not a native desktop.

## Explicit manual command

Build with `cargo build -p flux-native --features system --locked`. On a separate physical VT with a working seat broker, `fluxwm-native-probe --session --preview-output DEVICE:CONNECTOR` selects an explicit decimal udev device ID and DRM connector ID. Obtain those IDs from inventory/session output. This command changes physical display state. It has not been executed for this change.

The preview renders three solid RGB frames. The initial modeset completes synchronously; the second frame starts after that return, and the third starts after the matching second-frame flip. Later flips use NONBLOCK/PAGE_FLIP_EVENT; initial modeset and rollback do not request events. Its timer is registered before the first live submission. After 15 seconds, or SIGINT/SIGTERM, it attempts rollback. There is no keep option. The timer bounds event-loop scheduling, not synchronous kernel/library calls or total shutdown. Health requires the initial blocking completion and two distinct matching flip completions, no preview failure and successful rollback/cleanup. It does not measure physical photon timing or qualify driver behavior.

## Ownership and failure behavior

Rollback re-reads exactly the properties changed by the proposed request. It copies referenced blobs and clones framebuffer backing references through raw GETFB2/ADDFB2. Every distinct returned GEM handle closes once, including validation failures. This pins storage, not immutable pixel contents. Capture rejects unsupported property names/types, transient fences/writeback and oversized resource/blob sets. Both new and rollback states must pass TEST_ONLY; these checks do not reserve hardware against hotplug.

Rollback clones used for restored scanout close through CLOSEFB, which preserves attached planes. RMFB would disable those planes. Capture first creates and CLOSEFB-closes an unattached clone before retaining each rollback framebuffer. If rollback needs a nonzero framebuffer, a kernel without CLOSEFB support is rejected before the live modeset; RMFB cleanup of that unattached probe cannot affect scanout. Initial and later ioctl errors remain uncertain; a definite rejection is used only before the commit syscall. Successful synchronous rollback is the only native quiescence proof used to release front/pending targets.

One persistent pool bounds nominal prepared frame bytes/slots and output leases across GPU generations. One preview per GPU is admitted: the initial request can affect cloned routes and other planes, so concurrent independent rollback transactions are rejected. Combined multi-output transactions remain future work.

Seat loss, hotplug retirement, ambiguous rollback and cleanup failure preserve the complete output state, quota reservations and broker lease. They do not replay a stale topology or infer idle consumers. This deliberately retains resources while the process lives and can exhaust admission; it is containment, not completed VT/hotplug recovery. Retention does not survive process exit. An unexpected CLOSEFB failure after successful preflight can still leave registered restored clones that kernel exit cleanup removes, potentially blanking the restored output. Health fails; durable crash/error recovery remains unqualified. Cleanup failures are exposed separately in probe health. Graceful active-session shutdown attempts rollback before pausing DRM.

## Validation limits and next work

Fixtures exercise exact-cookie blocking completion, rollback failure retention/successful release, CLOSEFB capability-probe rejection/cleanup ordering, raw GETFB handle deduplication, property allowlists, commit flag policy and argument rejection. Device-free checks do not execute native reads, GBM allocation, atomic commit, rollback or CLOSEFB. Native compositor scene rendering/input/output publication, multi-output transactions, interactive persistent mode preview, restart stream freshness and physical session qualification remain open.

The Linux UAPI documents [blocking versus NONBLOCK atomic commits](https://docs.kernel.org/6.19/gpu/drm-uapi.html#drm-mode-atomic-nonblock), [GETFB2 GEM-handle ownership](https://docs.kernel.org/6.19/gpu/drm-uapi.html#drm-ioctl-mode-getfb2) and [CLOSEFB scanout preservation](https://docs.kernel.org/6.19/gpu/drm-uapi.html#drm-ioctl-mode-closefb). These contracts support the ownership design; they do not establish that an untested driver conforms.
