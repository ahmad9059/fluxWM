I found no HIGH or MEDIUM issues. The disconnect path holds up when traced through the pinned wayland-backend source, and the fixture's silent-peer check really does tell the two implementations apart. This is from reading the source only; I didn't run anything.

## Verified against source

- **Identity:** `live_window_client` (`crates/fluxwm/src/actions.rs:9`) goes from the generational `WindowId` to a live toplevel, then to `wl_surface().client()`, `ClientState`, and the `disconnected` flag. `disconnect_affected_windows` matches windows by exact `ClientId` equality. The backend's `get_client_mut` compares the full `InnerClientId` including its serial (`upstream/.../client.rs:743`), so a queued ID can't hit a reused slot. Nothing uses PID, title or app_id.
- **Kill and duplicate rejection:** `Client::kill` sets `killed` and calls `ClientData::disconnected` synchronously, inside `kill_client` (`client.rs:325`). So the atomic is already set before `apply_action` returns, and a second request to any window of that client is rejected. The callback only does an atomic store, so running under the backend lock is harmless.
- **Silent-peer cleanup:** `dispatch_client` always runs `cleanup()` after `dispatch_events_for` (`common_poll.rs:74-77`). `dispatch_all_clients` only cleans up after a non-empty epoll batch (`:91`). On a killed client, `next_request` returns EPIPE (`client.rs:350`); the client is removed from epoll; then `clients.cleanup` queues its destructors, does a final flush and drops the client. Dropping it closes the fd, which is what the fixture sees as POLLHUP. The author's reason for using single-client dispatch is correct.
- **Removing the dead windows:** the ping callback runs in one loop iteration, and `finish_dispatch` (`state.rs:1210`) runs in the after-dispatch hook. It removes dead roles, relayouts, restores focus, cleans up popups and grabs, and only then calls `drive_ipc`. So a later `windows.list` can't see the removed roles.
- **Ownership:** `Dispatcher` is an Rc shared between the registered source and the ping closure. Nothing points back to the loop, so there's no cycle. The `RefCell` borrow can't overlap because calloop runs callbacks one at a time.
- **Bounds:** `pending_client_disconnects` only grows for live, not-yet-disconnected clients, once per client. It's bounded by the number of connected clients and emptied with `mem::take` (any push made from a destructor goes into a new vec with a new ping).
- **Graceful close:** it checks the live client, then sends `send_close()` to the focused toplevel only. Nothing escalates.
- **Wire format:** `WireAction` uses `deny_unknown_fields` with `{}` variants. The test at `action.rs:133` covers `disconnect-client`. Nothing outside `ipc.rs:74` advertises it, so there's no default binding.

## LOW

1. **Doomed windows still look alive until the cleanup ping.** The backend's `object_info`/`get_client` don't check `killed` (`handle.rs:352,405`), so `window.alive()` stays true until cleanup runs. Only `DisconnectClient` and `CloseWindow` check the atomic. Trigger: one IPC client pipelines `disconnect-client` and then `restore-window <hidden sibling>`, `focus`, `fullscreen`, `maximize` or `minimize` (the last three act on the focused window, which may be the victim). Within the same `drive_ipc` batch, those are reported `accepted`, change the layout, bump the sequence, and send events that `send_event` silently drops for the killed client (`client.rs:126`). A pipelined `windows.list` would still list the victim's roles. Nothing breaks, because the next iteration cleans up. But "accepted" doesn't mean the target survives. Either use the `live_window_client` check in the window-addressed actions, or document the gap.
2. **The ping callback's `Ok` branch never runs.** For a killed client, `dispatch_single_client` always returns EPIPE, or `InvalidId` if the readable path cleaned up first. So every explicit disconnect logs "retired client dispatch" at debug level, and the request count never increases. Real failures look exactly like the normal case. Treat EPIPE/InvalidId as expected and log anything else.
3. **The IPC pre-check runs before `apply_action`'s guards.** `ipc.rs:124` calls `disconnect_affected_windows` before the stopping/shutdown check. During shutdown a stale ID reports "window is not a live toplevel" rather than "instance is shutting down". Only the error wording differs; nothing is mutated.
4. **Kill on the last loop iteration.** If the loop stops after a kill but before the ping is handled, the final `finish_dispatch` at `main.rs:466` never runs single-client cleanup. The client is only freed when the display is dropped. This only matters if teardown is ever expected to run the victim's destructors.

## What the fixture proves and doesn't

- **Solid:** after acceptance, the victim makes no requests or flushes, and the survivor's last flush happens before. IPC doesn't touch Wayland dispatch, and no other source drives `dispatch_all_clients` without a readable client. So POLLHUP within 350 ms (`main.rs:4134-4145`) discriminates, which matches the author's report that the dispatch-only version failed it. Targeting the unmapped role proves that neither focus nor mapping decides membership. The check that all three victim roles are gone and only the survivor remains (`:4179`) is a correct oracle.
- **Gap:** the "duplicate rejected before destruction" path is never exercised. The second request only arrives after cleanup, so it's rejected because the window ID is gone, not by the atomic. Pipelining two `disconnect-client` requests (victim, then hidden sibling) in one write would cover it, and the same test would show finding 1.
- **Gap:** the close check only asserts `windows[0].closes == 1`. Add `windows[1].closes == 0 && windows[2].closes == 0` to prove close goes only to the focused window.
- **Gap:** the stale rejection at `:4189` accepts any error. Assert the error code or message, so a transport or parse error can't pass as a rejection.
- **Redundant:** the transport check at `:4163` is already satisfied by the earlier POLLHUP.

Out of scope, as you asked: real hardware, toolkits, grab/clipboard matrices, the native backend and the C (sys) backend. All of the above applies only to the pinned Rust wayland-backend.
